Thirty seconds. Do not linger.

Press once for the three protocol cards. This room already knows MCP and A2A, so anchor there: same shape of problem, different edge of the system. MCP is the agent reaching for tools. A2A is agents talking to each other. A2UI is the agent reaching the human.
If someone asks about AG-UI: different thing, they compose. AG-UI is the transport between an agentic frontend and backend. A2UI is the format for the UI itself, and it can ride on AG-UI.
Version numbers are on the slide so nobody has to ask. It is real but still moving.

A2UI is a protocol, not a package

Nobody installs "A2UI". You install the renderer for your platform, and it speaks the format.

On Flutter you reach for the GenUI SDK. On the web you drop in the React, Angular or Lit renderer. Vercel and LangChain solve the same problem their own way, without A2UI.

Kill the "is it a library?" question before it is asked

Three presses: who sends, the wire, who draws.
Say it plainly: A2UI is a format, like JSON or HTTP. The thing you add to your app is a renderer.
Flutter's GenUI SDK is built on A2UI. That is the segue you use later, so plant it here.
If someone names a web framework you have not heard of: most of them are not renderers, they are agent frontends that wire one up for you. The renderer is the part that turns the JSON into your components.

So what actually changed?

The switch statement is gone. Everything else you already had, and the client still renders your own native widgets.

Walk the arrows, then land the one line

Three beats only. The agent bundles your catalog with the request. The model writes a recipe. Your app builds it from components you wrote.
Dwell on the validator, because it is the part people miss: the recipe is checked against the catalog before it is sent and again when it lands. "It cannot invent a widget" is a mechanism, not a promise.
Point at the catalog band. It is referenced three times in one round trip. That is why catalog quality is the whole job.
The arrow over the top is the loop. Most demos stop before it.
If asked what changed versus server-driven UI: you stop writing the mapping, it personalizes per request instead of per cohort, and it is an open wire format so the agent and the app can be different teams.

Why flat beats nested, 30 seconds

Nested JSON is only valid when complete. A flat list is valid the moment the first element closes. That's what makes progressive rendering possible.
Point at what's absent. That absence is the design-system guarantee.

STEP 1Define the schema

A JSON Schema for one component's props. Nothing about how it looks.

The description is not a comment. It is shipped to the model in the prompt, and it is the only reason the model knows when to reach for this component.

a2ui.org/guides/authoring-components

final itineraryDaySchema = S.object(
  description:
    'One day of a trip. Use when the user'
    ' wants a plan they can follow without'
    ' making decisions.',
  properties: {
    'day':   S.integer(),
    'items': S.list(items: S.string()),
  },
  required: ['day', 'items'],
);

The React renderer does the same thing with Zod. Same contract, different language.

STEP 3Define the catalog

Bind the name to the schema and the widget. This is the allowlist.

The catalog is the security model

A name that is not in this list has no builder, so it cannot render. You do not write a default case. You get one.

final appCatalog = Catalog([
  CatalogItem(
    name: 'ItineraryDay',
    dataSchema: itineraryDaySchema,
    builder: (data) => ItineraryDayCard(
      day: data['day'] as int,
      items: (data['items'] as List)
          .cast<String>(),
    ),
  ),
  // CostBreakdown, PackingList, ChipRow…
]);

When it goes wrong

Design the fallback before the happy path, because you will hit it in week one.

Unknown component

Not in your catalog, so it never renders. The rest of the surface survives.

Malformed JSON

The validator catches it and the agent gets a second try before anything reaches you.

Slow or down

Skeleton first, then your hand-written screen. Never an empty box with a spinner.

Offline

Last good response, or the static path. This is a product decision, not an error state.

Four presses. This is the slide people take a photo of.

Fail soft is in the spec, not in your code. Unknown names are dropped by the renderer. You still have to decide what the user sees instead.
The third card is where most teams lose. A spinner with no timeout is not a fallback.

A protocol

Declarative JSON between an agent and your app. Apache 2.0, from Google, currently v0.9.1.

Grounded on your catalog

The model picks names you wrote. Anything else is thrown away before it renders.

Rendered by you

Your widgets, your design system, your platform. Flutter, React, Angular or Lit.

Everything here is alpha.

A React renderer breakage recently needed web_core pinned below 0.8.4.
