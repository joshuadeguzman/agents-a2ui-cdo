How a request becomes native UI

a2ui.org/concepts/overview · adk.dev/integrations/a2ui · developers.googleblog.com · A2UI and MCP Apps

Data flow, 60 seconds

1. The user asks. 2. An agent answers with components from the app's catalog. It can be an ADK agent, an MCP tool, or your own backend. 3. Whatever sent it, it's the same A2UI JSON. 4. Each platform's renderer draws it with native widgets. 5. Taps go back to the agent, and the loop repeats.

Isn't this just server-driven UI?

Yes. A2UI is server-driven UI that any agent can speak.

The SDUI question, 60 seconds

Say it before someone asks. Airbnb, Lyft and others have shipped SDUI for years. A2UI is the same idea, made an open standard and shaped for models: a schema the model reads, a flat list that streams, renderers you don't maintain. The real gain is agents you don't own. A remote agent "cannot touch your UI directly; it must send messages." If you own both ends and know the screens, keep your SDUI.

Send light messages

3 ways to send UI from the cloud

MCP resource

resources/read returns a fixed surface. Settings, onboarding, a first-run home. No model call, so you can cache it.

MCP tool

tools/call fills a template from live data. Search results, a dashboard, today's numbers. The tool's parameters decide the screen.

A2A agent

The agent holds the whole conversation and composes the screen as it goes. Planning, comparing, anything open-ended.

from a2ui.core.schema.manager import A2uiSchemaManager
from google.adk.agents.llm_agent import LlmAgent
from google.adk.a2a.utils.agent_to_a2a import to_a2a

schema = A2uiSchemaManager(catalogs=[siargao_catalog])

agent = LlmAgent(
    model="gemini-3.5-flash",
    name="siargao_agent",
    instruction=schema.generate_system_prompt(
        role_description="You plan trips to Siargao.",
        include_schema=True,
    ),
)

a2a_app = to_a2a(agent, port=8080)

How to secure it

Keep API keys off the device

Call the model from Cloud Run, or through Firebase AI Logic with App Check turned on.

Give each service its own account

Least-privilege IAM per Cloud Run service. Agent Identity for agents on Cloud Run is in preview.

Only catalog components render

A component you didn't build can't render. That protects the layout, not the text inside it.

Filter prompts and responses

Model Armor on prompts and responses. Escape every string. Never render a URL you were handed.

Handling failures

Unknown component

Not in your catalog, so it fails validation. Catch it on the server and retry.

Malformed JSON

Validate on the server and give the agent a second try before anything reaches the user.

Slow or down

Show a skeleton, then your hand-built screen. Not an empty box with a spinner.

Offline

Show the last good response or the static screen.

When not to use A2UI

Checkout & login

People expect the same screen every time.

Screens you must audit

You need to show exactly what they saw.

Screens that must load instantly

Generating a screen takes seconds.

Only a few fixed answers

Just build those screens.

No design system

Generated screens will be as inconsistent as your components.

Offline screens

No connection means no agent.

Don't skip this when running late

This is what makes the rest believable.
You ship offline-first apps, so the last card is one you actually live with. Say that.

Key takeaways

A2UI is a protocol

JSON from an agent that your app renders natively. Open source from Google, v0.9 today.

Serve it from Cloud Run

MCP resources and tools for fixed and templated screens, an A2A agent for conversations.

Render it with your widgets

The model only arranges what you built.

Start with one generated panel from one MCP tool.

The one slide to photograph. Three presses, then stop.

The last line is the call to action. It is the smallest change that proves the idea in a real app.

Agent (agent/):
- Python ADK agent that emits A2UI v0.9 using the A2UI agent SDK (pip package a2ui-agent-sdk). Read https://adk.dev/integrations/a2ui/ and https://a2ui.org/guides/agent-development/ first. Target A2UI v0.9 and ignore v0.8 examples.
- Use A2uiSchemaManager with a custom catalog that matches the Flutter catalog names exactly. Generate the catalog JSON from one source of truth so the app and agent never drift.
- Validate every response against the catalog before sending. On validation failure, send a fallback text part, never broken UI.
- Expose it over A2A with an agent card that advertises the A2UI extension and the supportedCatalogIds.
- Model: default to the newest GA Flash-Lite model ID listed on the Vertex AI models page, configurable with a MODEL env var.
- Reference samples in https://github.com/a2ui-project/a2ui: samples/agent/adk/restaurant_finder and samples/community/agent/adk/gemini_enterprise/v0_9 (the Cloud Run sample from Google's "Host an A2UI agent with Cloud Run" tutorial).

Q&A, the ones you will get

MCP or A2A? MCP when the screen is a function of the tool's inputs. A2A when it depends on the conversation.
Cost per screen? Depends on model and catalog size. Fixed screens as resources cost nothing.
Prompt injection? Structure is safe by allowlist. Content is not.
Production ready? The pattern is. The spec is pre-1.0 and genui is alpha. Pin versions.
